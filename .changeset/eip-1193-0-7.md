---
'eip-1193-accounts-wrapper': minor
---

**eip-1193 0.7, declared as a dependency.** The published types import `eip-1193` but it was listed only as a devDependency, so an app type-checked them against whichever eip-1193 its package manager hoisted, and broke when something else brought 0.7 in. It now depends on `eip-1193` `^0.7.3`. Apps can drop the `packageExtensions` entry they added for it.

The provider slots move to the eip-1193 0.7 model, which is why this is a minor:

- `extendProviderWithAccounts(provider, options)` takes an `EIP1193CoreProvider` (was `EIP1193ProviderWithoutEvents`, which since eip-1193 0.7 is the browser-wallet surface and would reject a node provider). A wallet, a JSON-RPC node and an HTTP node provider are all accepted as is.
- It returns the new `EIP1193AccountsProvider` (`RequestRPC<AccountsProviderMethods>`, the core methods plus `eth_requestAccounts`), which fits any `EIP1193CoreProvider` slot. It used to promise the whole wallet surface, `wallet_*` included, which a wrapped node never served. A caller who knows the wrapped provider serves more names its table: `extendProviderWithAccounts<NodeMethods>(nodeProvider)`.
- New type exports: `EIP1193AccountsProvider`, `AccountsProviderMethods`, `EIP1193CoreProvider`. `EIP1193ProviderWithoutEvents` is still re-exported.

No runtime change. CI now builds, typechecks (including type tests that pin the slot types), tests, and checks that every package the published declarations import is a declared dependency; publishing goes through GitHub Actions with npm provenance.
